# 02 数据模型设计（MongoDB）

> 驿迹 ExpressTrace ｜ 对应需求：FR-01 ~ FR-10、BR-01 ~ BR-09
> 设计原则：**一单一文档轨迹内嵌 + 袋-件双层模型** —— 发挥文档数据库「按聚合根一次读取」与「批量写传播」的优势

## 1. 建模决策一：轨迹内嵌 vs 引用

| 方案 | 结构 | 评估 |
|---|---|---|
| **A. 轨迹内嵌订单文档（✅ 采用）** | `orders` 单集合，`tracking` 数组字段 | ① 查询「订单 + 全部轨迹」一次 `findOne` 完成，天然原子一致；② 订单与轨迹强归属、轨迹不跨单共享；③ 单订单轨迹量有限（数十条级），远低于 16MB 文档上限 |
| B. 轨迹独立集合 + 订单引用 | `orders` + `tracking_events` 两集合 | 适合轨迹量巨大或轨迹被多方引用的场景；但查一次轨迹要两次往返 + 应用层拼装，课程演示下无必要 |
| C. 混合：内嵌近期轨迹 + 归档旧轨迹 | 订单内嵌 + 历史归档集合 | 预留扩展方向，标准版不做（见 §8 演进） |

**结论**：方案 A，物流轨迹以子文档数组内嵌订单文档。这是文档数据库相对关系模型的典型优势点（关系模型必须拆两表做 JOIN）。

## 2. 建模决策二：袋-件双层模型（FR-08/09/10 的根基）

集包袋引入「一袋多件、整袋流转」的第二层聚合根。袋与件的关系建模：

| 方案 | 结构 | 评估 |
|---|---|---|
| **A. 袋独立集合 + 双向锚点（✅ 采用）** | `bags` 集合存 `order_nos` 件清单；`orders` 存 `bag_no` 当前袋号 | ① 袋作业（建袋/装件/封袋/扫描）以袋为聚合根一次写完；② 件上冗余 `bag_no` 支持反查「件在哪个袋」；③ 影响面分析用 `$lookup` 一条管道搞定 |
| B. 件内嵌袋文档 | 袋文档内嵌完整订单对象 | 冗余爆炸（订单主体数据重复 N 份），且订单更新要同步 N 处，否决 |
| C. 仅件存袋号 | 只有 `orders.bag_no`，无 `bags` 集合 | 袋级扫描记录、袋状态机、袋内清单无处安放，否决 |

**结论**：方案 A。`bags` 与 `orders` 两集合，通过 `bags.order_nos[]` 与 `orders.bag_no` 双向锚定；会籍互斥（BR-08）在应用层校验。

### 3.3 订单字段说明

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `order_no` | string | **唯一**，`ET`+`yyyyMMdd`+6位序列 | 业务主键，对外暴露的查询键（BR-03） |
| `sender` / `receiver` | object | 必填，含 name/phone/address | 寄件人 / 收件人（FR-01） |
| `package` | object | 必填 | 包裹信息：weight_kg、quantity、category、remark |
| `current_status` | string | 枚举（见 §4） | 当前物流状态，冗余自最新轨迹（BR-05） |
| `current_node` | string | 必填 | 当前所在网点，冗余自最新轨迹 |
| `bag_no` | string \| null | 默认 null，`BG`+`yyyyMMdd`+4位序列 | 当前所在集包袋；null 表示不在袋（BR-08） |
| `tracking` | array | 默认 `[]`，时序追加 | 物流轨迹子文档数组，按 `time` 升序（FR-02/03） |
| `tracking[].time` | date | 单调不减（BR-02） | 流转时间 |
| `tracking[].node` | string | 必填 | 所在网点 |
| `tracking[].action` | string | 必填 | 物流操作说明；袋扫件动写入的条目带 `[袋BGxxxx]` 前缀（BR-09） |
| `tracking[].status` | string | 枚举（见 §4） | 该节点的物流状态 |
| `created_at` / `updated_at` | date | 自动生成 | 下单时间 / 最后更新时间，供 FR-04 时间筛选 |

### 3.5 集包袋字段说明

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|

## 4. 状态枚举与状态机

### 4.1 订单状态（FR-07 / BR-01）

| 枚举值 | 中文 | 说明 |
|---|---|---|
| `CREATED` | 已创建 | 订单录入完成（FR-01） |
| `PICKED_UP` | 已揽收 | 快递员取件 |
| `IN_TRANSIT` | 中转运输 | 可出现多次（多级中转场） |
| `OUT_FOR_DELIVERY` | 派送中 | 到达派送网点，派件员派送 |
| `DELIVERED` | 已签收 | **终态**，此后禁止任何追加（BR-01） |

```
CREATED → PICKED_UP → IN_TRANSIT ⇄ (IN_TRANSIT)* → OUT_FOR_DELIVERY → DELIVERED
```

- 合法流转：指向下一个或同级可重复状态（`IN_TRANSIT` 多次）；
- `DELIVERED` 后追加任何轨迹 → 拒绝（HTTP 409）；
- 新轨迹 `time` 早于最后一条轨迹 `time` → 拒绝（HTTP 400）。

### 4.2 袋状态（FR-08 / BR-07）

| 枚举值 | 中文 | 触发扫描 type |
|---|---|---|
| `OPEN` | 建袋/装件中 | —（建袋初始态） |
| `SEALED` | 已封袋 | SEAL |
| `IN_TRANSIT` | 干线在途 | DEPART |
| `ARRIVED` | 已到港 | ARRIVE |
| `OPENED` | 已拆袋 | OPEN |
| `BROKEN` | 破损（异常） | EXCEPTION |
| `LOST` | 丢失（异常） | EXCEPTION |

```
OPEN → SEALED → IN_TRANSIT → ARRIVED → OPENED
                    │
                    └─→ BROKEN / LOST（吸收态，只进不出）
```

## 5. 建模决策三：袋扫件动——写传播 vs 读推导（核心创新点）

袋级扫描时袋内所有件的轨迹要同步推进（FR-09），两种机制：

| 方案 | 机制 | 写代价 | 读代价 | 评估 |
|---|---|---|---|---|
| **A. 写传播（✅ 采用为主）** | 袋扫描 → `updateMany` 为袋内全部件 `$push` 轨迹 + `$set` current_node | 1 次袋扫 = N 次件写（写放大 N 倍） | **零额外代价**：FR-03 一次 `findOne` 照常 | 课程规模 N≤百级，写放大可接受；读路径保持最简；件轨迹自带完整时间线，语义直观 |
| B. 读时推导 | 件轨迹 = 件自身扫描 ∪ 所属袋扫描（`$lookup` 按会籍窗口归并） | 零 | 每次查轨迹一条聚合管道 + 归并排序 | 写省读贵；FR-03 从 `findOne` 退化为 aggregate，查询语义变复杂 |
| C. 混合 | 袋扫描只写袋文档；拆袋时一次性回写件 | 折中 | 拆袋前件轨迹不完整 | 状态可见性窗口期问题，复杂度不划算 |

**结论**：方案 A 写传播为**主实现**；方案 B 读推导作为**对照实现**，两者构成可验证的对比实验（写传播耗时 vs 推导查询耗时），实验设计与预期见 `04-测试与部署.md` §4.3。这正是「一袋多件整袋流转」场景下文档数据库批量写能力的实证点——关系模型下该操作需要事务包裹 N 行 UPDATE，文档模型一条 `updateMany` 完成。

**写传播实现要点**：

```js
// 一次袋扫，件轨迹同步推进（示意）
db.orders.updateMany(
  { bag_no: "BG202611170001" },
  {
    $push: { tracking: { time, node, action: `[袋BG202611170001] ${action}`, status } },
    $set: { current_node: node, updated_at: time }
  }
)
```

- 传播动作与袋 `scans` 记录同事务语义（先后写袋、再批量写件；失败重放幂等靠 `action` 前缀 + time 去重）；
- 件轨迹 `action` 带 `[袋BGxxxx]` 前缀（BR-09），与件自身扫描可区分。

## 6. 整袋异常影响面分析（FR-10，聚合管道）

错袋/破损/丢失标记后，一条聚合管道圈出波及面：

```js
db.bags.aggregate([
  { $match: { bag_no: "BG202611170001" } },
  { $lookup: {
      from: "orders",
      localField: "order_nos",
      foreignField: "order_no",
      as: "orders"
  } },
  { $project: {
      bag_no: 1, dest_node: 1, status: 1,
      affected_count: { $size: "$orders" },
      orders: {
        order_no: 1, current_status: 1, current_node: 1,
        receiver: { name: "$receiver.name", phone: "$receiver.phone" }
      },
      status_dist: {
        $reduce: {
          input: "$orders",
          initialValue: {},
          in: { $mergeObjects: [
            "$$value",
            { $arrayToObject: [[{ k: "$$this.current_status", v: 1 }]] }
          ]}
        }
      }
  }}
])
```

- `$lookup` 按件清单联查订单（袋-件双向锚点的直接收益）；
- 输出：受影响件数、件明细、状态分布——「一袋错发波及哪些件」一问一答；
- 这是 FR-05（单键 `$group`）之上的聚合深度阶梯：`$group` → `$lookup` → `$project` 表达式计算。

## 7. 索引设计

| 索引 | 键 | 类型 | 服务的查询 |
|---|---|---|---|
| `idx_order_no` | `{ order_no: 1 }` | **唯一** | FR-03 按单号查全轨迹（等值） |
| `idx_status_created` | `{ current_status: 1, created_at: -1 }` | 复合 | FR-04 按状态 + 时间范围筛选（最常用组合） |
| `idx_node` | `{ current_node: 1 }` | 单键 | FR-04 按当前网点筛选 |
| `idx_created` | `{ created_at: -1 }` | 单键 | FR-04 纯时间范围筛选、列表默认排序 |
| `idx_bag_no` | `{ bag_no: 1 }` | **唯一**（bags） | FR-08 袋主键查询 |
| `idx_order_bag` | `{ bag_no: 1 }`（orders） | 单键 | FR-09 写传播按袋号圈件、影响面反查 |

设计说明：

- 优先把**等值条件放前、范围/排序条件放后**（`current_status` 等值 + `created_at` 范围）；
- `idx_order_bag` 服务写传播的 `updateMany({bag_no})` 与「查袋内全部件」——多键场景的核心索引；
- 建索引脚本：`data/init/02-create-indexes.js`；每个上线查询须附 `explain()` 输出，归档至 `document/`。

## 8. 聚合与统计（FR-05）

按状态统计订单数量，一条聚合管道覆盖：

```js
db.orders.aggregate([
  { $group: { _id: "$current_status", count: { $sum: 1 } } },
  { $sort: { _id: 1 } }
])
```

- 利用 `current_status` 冗余字段，**不需要** unwind 轨迹数组；
- 总量统计：`db.orders.countDocuments({})` 或管道中 `$group: { _id: null, total: { $sum: 1 } }`；
- 聚合深度阶梯：FR-05 `$group` → FR-10 `$lookup` 影响面（§6），由浅入深。

## 9. 容量与性能评估

| 指标 | 估算 |
|---|---|
| 订单单文档大小 | 基础 ~0.5KB + 轨迹 20 条 × ~0.2KB ≈ **4.5KB** |
| 袋单文档大小 | 基础 ~0.3KB + 件清单 100 单号 × ~0.02KB + 扫描 10 条 ≈ **2.5KB** |
| 10 万订单 + 千袋总量 | ≈ 455MB，远低于单集合/单文档限制 |
| 单文档 16MB 上限 | 订单可容 ~3500 条轨迹 / 袋可容 ~50 万单号，课程场景不可能触达 |
| 袋扫件动写放大 | 百级件 = 百级 `updateMany` 子写，单次毫秒~十毫秒级（实测见 04 §4.3） |

结论：双层模型在课程要求的数据规模下没有容量风险。
