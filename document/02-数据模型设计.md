# 02 数据模型设计（MongoDB）

> 驿迹 ExpressTrace ｜ 对应需求：FR-01 ~ FR-07、BR-01 ~ BR-05
> 设计原则：**一单一文档，轨迹内嵌数组** —— 发挥文档数据库「按聚合根一次读取」的优势

## 1. 建模决策：内嵌 vs 引用

| 方案 | 结构 | 评估 |
|---|---|---|
| **A. 轨迹内嵌订单文档（✅ 采用）** | `orders` 单集合，`tracking` 数组字段 | ① 查询「订单 + 全部轨迹」一次 `findOne` 完成，天然原子一致；② 订单与轨迹强归属、轨迹不跨单共享；③ 单订单轨迹量有限（数十条级），远低于 16MB 文档上限 |
| B. 轨迹独立集合 + 订单引用 | `orders` + `tracking_events` 两集合 | 适合轨迹量巨大或轨迹被多方引用的场景；但查一次轨迹要两次往返 + 应用层拼装，课程演示下无必要 |
| C. 混合：内嵌近期轨迹 + 归档旧轨迹 | 订单内嵌 + 历史归档集合 | 预留扩展方向，标准版不做（见 §7 演进） |

**结论**：标准版采用方案 A，`orders` 为唯一集合，物流轨迹以子文档数组内嵌。这是文档数据库相对关系模型的典型优势点（关系模型必须拆两表做 JOIN）。

## 2. 集合设计

### 2.1 数据库与集合

| 项 | 值 |
|---|---|
| 数据库 | `express_trace` |
| 集合 | `orders`（唯一集合） |
| 字符集/排序 | 默认 UTF-8 |

### 2.2 订单文档结构（Schema）

```json
{
  "_id": "ObjectId",
  "order_no": "ET20261117000001",
  "sender": {
    "name": "张三",
    "phone": "13800000001",
    "address": "广东省深圳市南山区科技园路1号"
  },
  "receiver": {
    "name": "李四",
    "phone": "13900000002",
    "address": "北京市海淀区中关村大街2号"
  },
  "package": {
    "weight_kg": 2.5,
    "quantity": 1,
    "category": "日用品",
    "remark": "易碎，轻拿轻放"
  },
  "current_status": "IN_TRANSIT",
  "current_node": "武汉中转场",
  "tracking": [
    {
      "time": "ISODate(\"2026-11-17T09:00:00+08:00\")",
      "node": "深圳南山营业点",
      "action": "已揽收，快递员王五取件",
      "status": "PICKED_UP"
    },
    {
      "time": "ISODate(\"2026-11-18T02:30:00+08:00\")",
      "node": "武汉中转场",
      "action": "快件到达武汉中转场，发往北京",
      "status": "IN_TRANSIT"
    }
  ],
  "created_at": "ISODate(\"2026-11-17T08:58:00+08:00\")",
  "updated_at": "ISODate(\"2026-11-18T02:30:00+08:00\")"
}
```

### 2.3 字段说明

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `order_no` | string | **唯一**，`ET`+`yyyyMMdd`+6位序列 | 业务主键，对外暴露的查询键（BR-03） |
| `sender` / `receiver` | object | 必填，含 name/phone/address | 寄件人 / 收件人（FR-01） |
| `package` | object | 必填 | 包裹信息：weight_kg、quantity、category、remark |
| `current_status` | string | 枚举（见 §3） | 当前物流状态，冗余自最新轨迹（BR-05） |
| `current_node` | string | 必填 | 当前所在网点，冗余自最新轨迹 |
| `tracking` | array | 默认 `[]`，时序追加 | 物流轨迹子文档数组，按 `time` 升序（FR-02/03） |
| `tracking[].time` | date | 单调不减（BR-02） | 流转时间 |
| `tracking[].node` | string | 必填 | 所在网点 |
| `tracking[].action` | string | 必填 | 物流操作说明 |
| `tracking[].status` | string | 枚举（见 §3） | 该节点的物流状态 |
| `created_at` / `updated_at` | date | 自动生成 | 下单时间 / 最后更新时间，供 FR-04 时间筛选 |

### 2.4 文档校验（validator）

集合创建时启用 JSON Schema 校验（`validationLevel: moderate`），保证状态枚举、必填字段、轨迹结构在数据库层不被破坏——校验脚本见 `data/init/01-create-collections.js`。

## 3. 状态枚举与状态机

| 枚举值 | 中文 | 说明 |
|---|---|---|
| `CREATED` | 已创建 | 订单录入完成（FR-01） |
| `PICKED_UP` | 已揽收 | 快递员取件 |
| `IN_TRANSIT` | 中转运输 | 可出现多次（多级中转场） |
| `OUT_FOR_DELIVERY` | 派送中 | 到达派送网点，派件员派送 |
| `DELIVERED` | 已签收 | **终态**，此后禁止任何追加（BR-01） |

状态机（应用层实现，对应 BR-01/BR-02）：

```
CREATED → PICKED_UP → IN_TRANSIT ⇄ (IN_TRANSIT)* → OUT_FOR_DELIVERY → DELIVERED
```

- 合法流转：指向下一个或同级可重复状态（`IN_TRANSIT` 多次）；
- `DELIVERED` 后追加任何轨迹 → 拒绝（HTTP 409）；
- 新轨迹 `time` 早于最后一条轨迹 `time` → 拒绝（HTTP 400）。

## 4. 索引设计

| 索引 | 键 | 类型 | 服务的查询 |
|---|---|---|---|
| `idx_order_no` | `{ order_no: 1 }` | **唯一** | FR-03 按单号查全轨迹（等值） |
| `idx_status_created` | `{ current_status: 1, created_at: -1 }` | 复合 | FR-04 按状态 + 时间范围筛选（最常用组合） |
| `idx_node` | `{ current_node: 1 }` | 单键 | FR-04 按当前网点筛选 |
| `idx_created` | `{ created_at: -1 }` | 单键 | FR-04 纯时间范围筛选、列表默认排序 |

设计说明：

- 优先把**等值条件放前、范围/排序条件放后**（`current_status` 等值 + `created_at` 范围）；
- 网点筛选标准版基于 `current_node`（冗余字段）；若需「途经网点」语义（轨迹数组中任一节点匹配），查询用 `tracking.node` + 多键索引 `{"tracking.node": 1}`，作为 FR-04 增强项，见 `03-接口设计.md` 备注；
- 建索引脚本：`data/init/02-create-indexes.js`；每个上线查询须附 `explain()` 截图/输出，归档至 `document/`。

## 5. 聚合与统计（FR-05）

按状态统计订单数量，一条聚合管道覆盖：

```js
db.orders.aggregate([
  { $group: { _id: "$current_status", count: { $sum: 1 } } },
  { $sort: { _id: 1 } }
])
```

- 利用 `current_status` 冗余字段，**不需要** unwind 轨迹数组；
- 总量统计：`db.orders.countDocuments({})` 或管道中 `$group: { _id: null, total: { $sum: 1 } }`。

## 6. 容量与性能评估

| 指标 | 估算 |
|---|---|
| 单文档大小 | 订单基础 ~0.5KB + 轨迹 20 条 × ~0.2KB ≈ **4.5KB** |
| 10 万订单总量 | ≈ 450MB，远低于单集合/单文档限制 |
| 单文档 16MB 上限 | 可容纳 ~3500 条轨迹，课程场景不可能触达 |

结论：方案 A 在课程要求的数据规模下没有任何容量风险。

## 7. 演进预留（标准版不实现，写入文档防止返工）

| 触发条件 | 演进方向 |
|---|---|
| 单订单轨迹 > 数百条 | 冷轨迹拆出 `tracking_events_archive` 集合，订单内只留最近 N 条（方案 C） |
| 轨迹写入并发要求高 | 轨迹独立集合 + 稀疏索引（方案 B），订单保留摘要 |
| 需要全文检索操作说明 | `tracking.action` 建 text index |
